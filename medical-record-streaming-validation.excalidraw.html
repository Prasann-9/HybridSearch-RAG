Hybrid search decision guide

Hybrid search runs a lexical (keyword/BM25) path alongside vector search and fuses the two ranked lists. It earns its cost when meaning alone or keywords alone cannot reliably find the right passage.

When to use hybrid search Use it when exact terms, IDs, jargon, or rare tokens matter as much as meaning and paraphrase.
Architecture flow Query -> dense (vector) path and sparse (BM25) path in parallel -> fuse rankings -> optional rerank -> generate.
When not to use it Avoid it for purely conceptual queries, ultra-low-latency paths, or corpora already well covered by one method.

    When to use hybrid search

    Use hybrid search when a single retrieval signal, dense or sparse alone, leaves recall gaps.

    Use

    Exact IDs, codes, or entities matter

    SKUs, error codes, ticket numbers, legal citations, and function names need literal token matches that embeddings often blur.

    Use

    Domain jargon and acronyms

    Specialized vocabulary that is rare or out-of-vocabulary for the embedding model benefits from an exact keyword signal.

    Use

    Mixed query styles

    Some users ask conceptual questions, others paste exact terms. Fusing both signals serves both styles from one system.

    Use

    Long-tail or rare terms

    Infrequent terms are underrepresented in embedding space but can still be found reliably by exact lexical match.

    Use

    Typo-prone or multilingual input

    Where one signal is noisy (typos confuse BM25, code-switching confuses embeddings), the other signal can compensate.

    Use

    Known recall gaps in vector-only search

    If evals show vector search alone misses relevant passages that keyword search would catch, fusion recovers that recall.

    When not to use hybrid search

    Hybrid search adds a second index and a fusion step. Do not add it when a single method already satisfies the need.

    Avoid

    Purely conceptual queries

    If users always ask in natural language with no exact terms to match, a well-tuned vector search alone is usually sufficient.

    Avoid

    Very tight latency or cost budget

    Running two retrieval paths plus fusion adds latency and infra cost. If the budget is ultra-low, a single method is safer.

    Avoid

    Small, homogeneous corpus already well covered

    If the corpus is narrow and one method already gets strong recall and precision in evals, hybrid adds complexity without benefit.

    Careful

    No infra or ops budget for a second index

    Maintaining a keyword index and fusion logic alongside a vector store is ongoing operational overhead, not a one-time cost.

    Careful

    Unvalidated fusion weights

    Without evals to confirm the lexical path actually improves results, poorly tuned fusion can hurt ranking quality instead of helping.

    Careful

    A reranker or better chunking closes the gap cheaper

    Sometimes improved chunking, metadata filters, or a cross-encoder reranker over vector-only results fixes recall more cheaply than a second index.
